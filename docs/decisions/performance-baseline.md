# 性能基线（启动耗时与空闲内存）

**测量方式**：`scripts/bench-baseline.sh`（release 产物；可直接复现）
**最近一次测量**：2026-10-02 · macOS 13.7.8（Build 22H730）· load ≈ 4.6 · 插电机

## 实测结果

| 指标 | 实测 | 判据 |
|---|---|---|
| `mc-cli doctor` 冷启动 | p50 **249ms** · p95 924ms · max 924ms（n=5） | p50 < 1s（doctor 要能当自检入口随手跑） |
| daemon 冷启动 → `/api/health` 就绪 | **1115ms**（单次） | < 5s |
| daemon 空闲 5s 常驻内存（RSS） | **11.4 MB** | < 200MB |
| `/api/diagnostics` 字段 | 齐全（platform / retention / components / queues / invariants） | 齐全 |

## 复现命令

```bash
./scripts/bench-baseline.sh --runs 5 --idle 5
```

## 局限（不要把这些数字当微基准）

1. **daemon 就绪只测了单次**：写成 p50/p95 需要在同一台机器上跑 N 次；
   当前是「有一次真实数值」，用来发现数量级变化足够，用来做容量规划不够。
2. **p95 明显高于 p50**（249ms → 924ms）：本机负载在 4–29 之间波动，
   首次运行还要付页缓存代价。跨机器比较这两个数字没有意义。
3. **沙箱里没有屏幕录制权限**：采集环会持续失败并写 `pipeline_failures`，
   因此这次的内存数字包含「失败路径」的开销，不包含真实截图与图片编码。
   有权限的机器上 RSS 会更高（也要重新测）。
4. **这些阈值是数量级护栏**，不是 SLA。真正的 SLA（像素路径 p50 < 100ms /
   p95 < 250ms）需要真机与权限才能测（判据与命令在本机留档）。

## 为什么单独用脚本而不是 cargo 测试

这两项测的是**进程级**行为（冷启动到就绪、静置后的 RSS）。用 cargo 测要在
测试里再起进程、再采样，慢且不稳；脚本直接测用户真正拿到的 release 二进制。
