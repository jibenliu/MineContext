## 1. 产品是什么

截图 + 内容理解 → 上下文工程 → 主动产出总结 / 待办 / 提示。

一句话结论：**「采集成功」不等于「上下文管线成功」。** 采集（截图、窗口）相对容易，
难的是把采集到的东西**可靠地**变成长期有价值的信息 —— 阶段总结、可检索的历史、能追溯到证据的结论。

因此这个产品的验收标准不是「截到了多少张图」，而是：

1. **该有的总结一定有**：阶段结束就产出总结，模型不可用时用确定性兜底，绝不静默不产出；
2. **说的每句话都有出处**：总结与问答的结论都能回溯到具体观测（截图 / 窗口），
   区分「观察到的事实」与「模型推断」；
3. **出错时用户看得见**：每个失败都有错误码、严重级别、补救建议，而不是一句「生成失败」；
4. **长时间运行不失控**：磁盘、内存、模型花费都有明确的上界与下降路径。

## 2. 要解决的问题

原文按性能 / 稳定性 / 体验 / 通用性 / 架构 / 数据质量六个维度拆解，这里按它自己的编号保留，
只留结论与证据。

| # | 问题 | 症状与证据 |
|---|---|---|
| 1 | 最大的成本不是截图，而是截图之后的 AI 管线 | 20 秒一张截图，但同一张图在 **2 秒内被请求 3 次**（Issue #255）；15 秒/张 × 双屏 ≈ **3840 张/天** |
| 2 | Token 成本与实际价值不匹配 | **2 小时 300 万+ Token，UI 没有产生总结**（Issue #50）；连续编码场景 **95% 内容重复** |
| 3 | 「无法加载上下文类型」是架构体验问题 | `截图 √ → Context Type × → Summary ×`，下游检索/待办/总结/问答一起塌 |
| 4 | 截图分析链路脆弱 | 升级到 0.18 后缺少 `screenshot_analyze` 提示词 → 分析持续失败（Issue #342）；`ExtractedData summary` 校验失败（#351） |
| 5 | 「OpenAI Compatible」≠ 真正的 Provider 抽象 | 自定义 embedding 服务走的是豆包 SDK 的 `multimodal_embeddings()` → `AttributeError`，UI 只显示 timeout（#355） |
| 6 | 错误提示是黑盒 | 真实错误是 `AttributeError`，用户看到的是 `timeout / validation failed`，最终只有一句「生成失败」 |
| 7 | 长期运行不稳定 | Windows 上运行约 **2 小时占用 > 8GB** committed memory（#179）；PIL 句柄未释放 |
| 8 | 时间处理不统一 | naive 与 aware datetime 混用 → `can't compare offset-naive and offset-aware datetimes`（#368）；波及日报/周报/待办/检索/调度 |
| 9 | 错误恢复能力不足 | `VLM 失败 → 这条上下文消失 → 用户不知道`；embedding 失败会阻塞截图采集 |
| 10 | 采集与智能耦合过深 | 「一直在截图」但后面的处理已经积压：队列↑ 延迟↑ 内存↑ Token↑ |
| 11 | 「截图」太中心化 | 更准确说是 *Screen* Context Agent，不是 Personal Context Engine |
| 12 | 截图信息密度低 | 侧栏/页脚/广告/导航都进 VLM；网页表格与长文档一张图就是一大笔 Token |
| 13 | 数据质量：Context 看起来智能但不一定可靠 | 看到 Jira 就推断「正在开发 APEX-388」，而用户只是在翻历史需求 —— 观察与推断混在一起 |
| 14 | 用户缺少修正手段 | 模型判断错了，用户没有办法把它改回来 |

原文的优先级排序（第十五节）：**P0** 上下文类型加载、截图分析失败、模型错误无法反馈、
长时间运行资源失控；**P1** 重复请求、Token 过高、提示词/Schema 强耦合、自定义 Provider 不兼容、
时间处理不统一、采集与处理耦合；**P2** 信息密度、来源单一、provenance 不完整、缺少修正机制。

## 3. 逐条对照：现在到哪一步

状态口径：**已解决** = 有实现 + 有门禁或测试；**部分** = 主干在、缺口明确列出；
**未做** = 明确没做（不假装完成）。

| # | 问题 | 状态 | 现在的做法与证据 | 还剩什么 |
|---|---|---|---|---|
| 1 | 重复消费同一张图 | 已解决 | 观测带**幂等键**（内容哈希 + 源 + 时间桶）唯一索引，重复投递只留一行；变化检测把「没变化的帧」在落盘前挡掉 | —— |
| 2 | Token 花得不值 | 已解决 | 分级调度（正常 / 合并冗余 / 只分析重大变化）+ **预算硬闸门**（60 分钟桶 + 24 小时桶，超限不再调模型但廉价元数据照记）+ 逐次调用记账（token 与成本可查） | 面向个人用户的成本策略仍可细调 |
| 3 | 上下文类型加载失败 | 已解决 | 类型（观测 / 活动 / 阶段 / 总结）与兼容层在**同一个二进制**里，不存在「元数据层单独挂掉」；17+ 条接口由真进程冒烟覆盖 | —— |
| 4 | 分析链路对提示词 / Schema 强耦合 | 已解决 | 提示词**编译进二进制**（缺失或改坏都不可能让分析整体停摆），`check-prompt-embedded.sh` 保证每个模板都被引用；模型输出解析失败一律降级到「观察到」并保留原始输出 | 模板目前不开放用户自定义 |
| 5 | 自定义 Provider 不兼容 | 已解决 | 只依赖 OpenAI 兼容的接口形状（chat / embeddings）与一个 HTTP 传输抽象，**没有任何厂商 SDK**（`check-provider-purity.sh` 把关）；向量维度从响应推断而非写死 | —— |
| 6 | 错误黑盒 | 已解决 | 每个错误带 `error_code` / `component` / 严重级别 / 可重试性 / 补救建议；失败落 `pipeline_failures`，诊断页与可分享诊断包都能看到；日志里也能按 `component` + `event` 过滤 | —— |
| 7 | 长时间运行资源失控 | 部分 | 保留策略（按天数 / 总字节 / 条目数）+ 悬空引用清理 + 任务租约回收 + 崩溃恢复；截图与缩略图落文件系统，数据库只存路径与哈希 | **8 / 24 / 72 小时真机长跑未执行**（脚本已就绪，见 `verify-external.sh`） |
| 8 | 时间处理不统一 | 已解决 | 领域层唯一时间表示是 UTC 毫秒（`Timestamp`），时区只在展示与日边界处按 IANA 名称转换；`check-no-naive-datetime.sh` 禁止 naive 类型进生产代码 | —— |
| 9 | 错误恢复不足 | 已解决 | 采集只负责产出观测、绝不等待分析；失败重试 + 指数退避 + 终态记录 + 单条失败不阻塞整轮；采集与视觉、总结各有独立容量池 | —— |
| 10 | 采集与智能耦合 | 已解决 | `Event → Activity → Stage → Summary` 事件溯源；采集环、投影、语义索引、保留策略是**四个独立循环**，互不阻塞 | —— |
| 11 | 来源单一 | 部分 | 采集源抽象支持 screen / window（本机可用）与 **clipboard**（已实现：默认关闭，需在 capture.sources 里显式点名；落库前过脱敏，脱敏规则非法时不落库；真机端到端未验）；file / browser 仍在类型与配置里预留并在启动时如实报告「尚未实现」 | 剪贴板、文件、浏览器采集 |
| 12 | 信息密度低 | 部分 | 变化检测（像素差分级）先过滤，隐私规则在落盘前拦截；窗口观测带应用名与标题，成本远低于整图 | OCR / 廉价抽取器这条路径还没接 |
| 13 | provenance 不完整 | 部分 | 活动带**来源**（观察到 / 规则命中 / 模型推断）+ 置信度；总结重生成走「新写一条 + 标记旧的被取代」，不就地覆盖 | 「被否决」的显式建模、跨源关联 |
| 14 | 用户修正机制 | 已解决 | 用户修正**先作为事件落库**再重算派生表（顺序不能反），因此重放不会丢掉修正 | 修正入口目前只有接口层 |

## 4. 关键设计对策

1. **事件溯源**：原始事实（事件、观测）不可变，派生数据（活动、阶段、总结）随时可重建。
   改算法不需要迁移历史数据 —— 重放即可。代价是存储与投影逻辑要写对。
2. **采集 ≠ 智能**：采集环只做「取一帧 → 变化检测 → 隐私过滤 → 落盘落库」，
   分析由独立循环按自己的节奏消费观测。模型慢、限流、掉线都不会让采集停摆。
3. **先便宜后昂贵**：像素级变化检测 → 廉价元数据（进程名 / 窗口标题）→ 规则 → 才轮到模型。
   每一次模型调用都要先过四道闸门（规则已判 / 预算 / 同窗口复用 / 滑动窗口限流）。
4. **降级必须可见**：没有模型也要有总结（确定性兜底），但兜底会被明确标记质量等级，
   界面必须把「模型写的」与「模板套的」分开显示。
5. **错误是一等公民**：错误码挂在错误类型上，组件、严重级别、是否可重试、补救建议由编译器强制补齐。
6. **数据库只存路径与哈希**：图片落文件系统，清理策略才有明确的下降路径；
   引用与文件由保留策略一起维护（只删文件会留下破图，只清引用会泄漏磁盘）。
7. **隐私是路径上的关卡**：拦截发生在落盘之前，脱敏发生在出网之前，两者分开；
   被拦截的内容不参与检索（包括向量检索），否则换个方式就能捞回来。
8. **时间只有一个表示**：UTC 毫秒；时区只在边界处出现。

## 5. 性能与成本的账

原定目标值与现状（「未纳入门禁」= 目前没有自动化的判据，
只能人工或长跑观察）：

| 指标 | 目标 | 现状 |
|---|---|---|
| 截图耗时 | < 100 ms | 未纳入门禁（受多屏与分辨率影响） |
| 本地分析（变化检测等） | < 500 ms | 未纳入门禁 |
| 活动识别 | < 1 s | 由投影节奏决定，未单独计时 |
| 界面操作响应 | < 100 ms | 未纳入门禁 |
| 空闲内存 | < 300 MB | 未纳入门禁（真机长跑时观察） |
| 空闲 CPU | < 3% | 未纳入门禁 |
| 模型失败恢复 | < 30 s | 退避重试 + 租约回收，租约超时可配 |
| 崩溃恢复 | 自动 | 已实现：启动时把上次未收尾的阶段补记为「被中断」 |
| 队列积压 | 可观测 | 已实现：诊断接口暴露待分析队列长度与失败分布 |
| 24 小时稳定运行 | 通过 | **未执行**（脚本就绪） |
| 内存泄漏（24h RSS 增长） | < 10% | **未执行** |
| 活动识别准确率 | ≥ 90% | 未测（需要人工标注的黄金数据集） |
| 应用识别准确率 | ≥ 98% | 未测 |
| OCR 准确率 | ≥ 95% | 未做 OCR |
| 阶段切分 F1 | ≥ 85% | 未测 |

**成本侧已有明确上界**：预算闸门按滑动窗口限制模型调用次数与 token，超限后停止调用模型
但继续记录廉价元数据；每次调用的 token 与成本都进账，可回答「今天花了多少、做出来了什么」。

## 6. 同类产品对比

原文的对比表（✅ = 支持；成熟度是原作者的星级判断）：

| 工具 | 持续截图 | 自定义 VLM | 本地运行 | 上下文 / 历史 | 免费 | 成熟度 |
|---|---|---|---|---|---|---|
| **Mnemora** | ✅ | ✅ | ✅ | ⭐⭐⭐⭐⭐ | ✅ | ⭐⭐⭐ |
| **DeskMate** | ✅ | 可扩展 | ✅ | ⭐⭐⭐⭐ | ✅ | ⭐⭐⭐ |
| **Vision Local Context** | 需自己调度 | ✅ | ✅ | ⭐⭐ | ✅ | ⭐⭐⭐ |
| **Open Interpreter** | 按需 | ✅ | ✅ | ⭐⭐ | ✅ | ⭐⭐⭐⭐ |
| **OpenAdapt** | ✅ | 有视觉能力 | ✅ | ⭐⭐ | ✅ | ⭐⭐⭐⭐ |
| **MineContext（本产品）** | ✅ | ✅ | ✅ | ⭐⭐⭐⭐ | ✅ | 自研 |

原文的三个结论：

1. **最接近需求的是 Mnemora**：截图 → OCR/VLM → 结构化上下文 → 时间线 → 阶段总结 → 检索，
   且 VLM / LLM / Embedding 都可自配；它的「20 分钟活动窗口」与「25 分钟以上深度工作」
   和本产品的阶段总结属于同一问题域。
2. **长期稳定优先则看 DeskMate**：它不只依赖 VLM（无障碍树 + OCR + 截图 + 用户行为 → SQLite），
   「这种架构更适合长期 24 小时运行」，代价是自定义模型只算「可扩展」。
3. **「免费」有两层**：软件免费容易，**推理也 $0 需要本地 VLM**（Ollama / LM Studio + Qwen3-VL 之类），
   否则接云端 API 时「软件免费但截图识别照样产生成本」。

原文还给了 6 个「截图成功 ≠ 上下文系统正常」的实测指标：截图稳定性、VLM 队列是否堆积、
失败是否自动重试、阶段总结是否按窗口生成、上下文能否跨应用关联、8–12 小时是否内存/磁盘失控。
这 6 条与本产品的验收口径一致，其中前 5 条已由门禁与诊断接口覆盖，第 6 条属于长跑项。

**本产品相对它们的差异**：把「可靠性」当成主要目标 —— 总结一定产出（兜底可见）、
结论一定可追溯（来源 + 证据）、错误一定可解释（错误码 + 补救建议）、
成本一定有上界（预算闸门）、历史一定可重建（事件溯源）。

## 7. 已知缺口与未验证项

**功能缺口**

- 剪贴板 / 文件 / 浏览器采集未实现（配置里点名时会在启动日志里如实报告，不会悄悄退回整屏）；
- 浏览器 URL 级隐私规则缺失，`blocked_domains` 目前只有窗口标题启发式；
- OCR / 廉价抽取器未接，截图理解完全走视觉模型；
- 「屏幕截图里后台运行的拉黑应用」尚未拦截；
- 提示词模板：配置项 `summary.template_id` 与 `summary.template_yaml` 已接通校验与记录
  （未知 id、坏 YAML 都明确报错，落库记录写实际使用的模板），模板会被真正用于生成（模型与兜底两条路径都用它）；
- 桌面外壳：**Tauri 2（唯一）**（托盘只有显示窗口/退出、单实例锁、系统通知、
  开机自启、未签名 dmg）；渲染层日志写 `<日志目录>/renderer.log`；**没有自动更新**
  （需签名与公证）、多窗口状态同步是 no-op；窗口/托盘观感与「系统通知是否真的
  弹出」仍属人工确认项；
- **任意时段总结**：四条入口都已接 —— 预设按钮、时间轴**拖选**、深链
  `#/summaries?from=&to=`（分钟级精度不会被折成整天）、对话指令（命中即走本地作业、
  不发给模型）。唯一遗留：从对话触发的作业，进度/取消界面仍在总结页；
- **活动来源与改名**：时间线已能区分「观察到 / 规则 / 推测（含模型名与置信度）」，
  改名、**并入上一条**、**按时刻切分**都已有界面；
- **磁盘将满降级**：已接线 —— 余量低于 512 MiB 时跳过该轮采集并写一条节流的可见
  失败，恢复后自动继续（**未在真机灌满磁盘验证**）；
- **批量回填有 API/worker、缺界面入口**：`POST /api/v1/jobs/backfill` 与 daemon 消费者已通，设置/诊断页尚未暴露；
- **活动推断用量已记账**（`record_inference_calls` → `provider_calls`）；语义索引现覆盖活动与笔记，总结向量仍未建。

**未验证（外部条件）**

- 8 / 24 / 72 小时真机长跑与内存增长；
- 黄金数据集上的准确率（活动 / 应用识别 / 阶段切分）；
- macOS 安装包签名与公证（无签名身份，产物未签名）；
- 新机（无开发环境）上的安装与首次运行人工确认。

**怎么核对**

```bash
./scripts/verify-all.sh          # 全部门禁：契约、lint、格式、clippy、测试、真进程冒烟、前端
./scripts/verify-external.sh     # 需要外部条件的项（未执行时输出 SKIP，不算通过）
mc-cli doctor                    # 五段自检：config / storage / model / platform / capture
```

逐条问题的原始证据与编号见内部问题清单（随开发过程留档，不入库）；每片改动的红→绿证据记在本地 TDD 日志。
